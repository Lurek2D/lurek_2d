# create-test-evidence

## Mission
- Create or modify evidence tests that produce durable artifacts for public Lua behavior.
- Keep canonical `tests/lua/evidence/test_<module>_evidence.lua` files module-owned and focused on APIs that the produced artifact genuinely demonstrates.
- Treat evidence as artifact generation: the block should pass when it successfully emits the intended screenshot, audio, text, JSON, or similar proof artifact.
- Treat golden as a separate comparison layer: a golden test should validate a newly produced artifact against a stored baseline rather than merely producing the artifact.

## Domain Knowledge
- Evidence tests answer “can a reviewer see the behavior?” rather than “did an assertion pass?”; their contract is the legibility and provenance of artifacts under `tests/artifacts/current/<module>/`.
- Ownership comes from `test_<module>_evidence.lua` plus the produced artifact, not `@covers` metadata. Helper exporters such as `image.savePNG` are sinks and do not become evidence owners.
- The `Does`/`Shows`/`Artifact`/`Why` rationale explains behavior, visual encoding, output path, and review value; it should make weak evidence recognizable before the test is run.
- Current artifacts and baselines serve different roles: evidence writes current output, while golden tests compare reviewed baselines. Updating a baseline is an explicit acceptance decision, never a side effect of evidence generation.
- Evidence and reseed scripts share `.lua_artifacts.lock` because concurrent writers can create mixed current/baseline state that looks like product drift.
- Artifact format should match the behavior: images for spatial output, structured text or tables for state transitions and serialization, and logs only when ordering or diagnostics are the subject. Choosing an easy exporter over a legible format weakens proof.
- Deterministic evidence controls seed, viewport, frame count, asset inputs, output ordering, and numeric formatting so review differences correspond to behavior rather than ambient state.
- Reference marks, labels, contrasting cases, or before/after panels should be generated by the scenario when they help a reviewer interpret output without opening the test source.

## Workflow
- Start from evidence/non-unit audits and inspect the target behavior plus existing current/baseline artifact; state what a human must be able to distinguish, which owner API creates it, and why textual assertions or an example are insufficient.
- Design a deterministic scene/dataset with controls or reference marks that reveal the effect, write the four-line rationale immediately above its `it()`, and emit a descriptive module-local current artifact without coverage markers or baseline writes.
- Run through the canonical locked artifact path, open the result, and reject technically valid but ambiguous output—blank frames, tiny differences, unlabeled tables, or artifacts dominated by exporter/helper behavior.
- Rerun evidence and non-unit contract audits; when golden comparison is requested, review current versus baseline before using the canonical reseed command, rerun the comparison, and record why the accepted difference is intentional.
- Design the artifact filename and directory before coding, checking for collisions with existing module evidence and ensuring a cleanup/reseed operation can identify the exact owner without deleting another scenario's output.
- Run from a clean current-artifact state and again without cleanup, confirming the test overwrites or deterministically recreates only its owned files and does not depend on leftovers from the first run.
- Inspect artifacts at normal review scale and through any manifest/catalog consumer; include labels, bounds, legends, or paired cases needed to make the target behavior immediately distinguishable.
- When behavior has both qualitative and exact requirements, pair evidence with unit assertions rather than embedding pass/fail assertions into the evidence layer; keep each proof at its canonical owner.
